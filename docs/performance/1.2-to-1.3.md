# Programmable-block performance review: 1.2 through current 1.3 development

Date: 2026-10-03. Minecraft Forge 1.12.2, Java 8.

The common-block follow-up has now been implemented; see [changes and validation](COMMON_BLOCK_OPTIMIZATION.md). The historical findings below describe the reviewed endpoint before those fixes.

**The highest-priority problems are repeated trapdoor assembly work, new geometry allocation in wall/porthole rendering, and expensive diagonal-trapdoor collision generation.** Ordinary Programmable Blocks, Slabs and Stairs still use cached chunk models; the changes do not put their static housing back into a per-frame tile renderer. A room built primarily from those blocks should behave very differently from one filled with diagonal portholes, joined trapdoors and animated displays.

There are also new costs outside the visible blocks: offset-leaf picking runs even in empty scenes, and the expanded texture catalog consumes memory even when its materials are unused. Redstone remains event-driven, but joined trapdoors repeat expensive work for each recipient of the same channel change.

## Scope and evidence

Baseline: **`0b8ac9dd1b3b9cea02f42fcc0112db02156731c4`**, the final commit before the initial 1.3 release, with `version = '1.2'`.

Reviewed endpoint: **`d24338e4d1f2666a4429a1df88830e74a7fa0c6f`**, still labeled 1.3 in `build.gradle`. This covers **60 commits**, including changes currently listed under **Unreleased**. It is broader than the initial `310e710e` 1.3 release. Source references below describe this endpoint.

| `8e1ba547`, `941f4a3b`, `49ddc38d` | Larger rectangular and staggered trapdoor assemblies, shared opening directions and partial patches. |
| `af1dfedf`, `597d4508` | Shared material atlas entries, filesystem textures, custom block materials, static display surfaces and landing-gear covers. |

| `c1512ea8` | Diagonal neighbor clipping, revised porthole mesh generation, expanded diagonal connections and surface sliding. |

Evidence consists of the Git diff, current call paths, three sequential runs of a Java CPU probe, and texture pixel accounting. The probe uses real mod methods in a minimal in-memory world, with no renderer. **These are not whole-client 1.2-versus-1.3 benchmarks, GPU timings, FPS measurements or shader validation.** New trapdoor features have no equivalent implementation in 1.2; their grouped/ungrouped measurements characterize added cost. One narrow porthole comparison reproduces the old direct vertex-emission code against the new helper.

No production code was changed. No live client suite was run: the changes here are documentation and standalone diagnostics. A hardware client comparison remains necessary to measure the total regression in a real build.

## 1. Trapdoor rendering repeats work that belongs to the assembly

Sources: [trapdoor renderer](../../src/main/java/com/vandorlabs/client/TEProgrammableTrapdoor.java), [base tile](../../src/main/java/com/vandorlabs/tiles/TileEntityProgrammableTrapdoor.java), [diagonal tile](../../src/main/java/com/vandorlabs/tiles/TileEntityProgrammableDiagonalTrapdoor.java).

`TEProgrammableTrapdoor.render()` performs an individual buffer begin/draw and GL-state setup for each leaf, including stationary leaves. It regenerates corner arrays, texture coordinates and surface-clipping data every frame. Joining leaves does not merge these draw calls.

The more serious scaling issue is `group()` (base tile, lines 109–137). For an assembly of **n** leaves it visits all n positions and compares its n-entry membership list with each other member's list. That is approximately **O(n²) validation per call**, repeated by every rendered leaf. For one fully visible assembly, one group lookup per leaf therefore approaches **O(n³)** list-comparison work, bounded by the 64-leaf limit. Across independent assemblies, the cost is additive rather than cubic in the entire scene's block count.

`materialCoordinates()` calls `group()` and scans group bounds. For tall diagonal leaves, the closed-corner calculation calls `rotationReverse()` or `slideLiftDirection()`, which validates and scans the group again. Drawing the current pose adds another such calculation. None of this requires the leaf to be moving.

Measured CPU time for **texture-coordinate preparation only**, holding total leaves at 64:

| Layout | Median time per 64 leaves | Median allocated bytes |
| --- | ---: | ---: |
| Regular, 64 independent leaves | 0.0169 ms | 98,304 |
| Regular, four groups of 16 | 0.0342 ms | 110,080 |
| Regular, one group of 64 | 0.1563 ms | 153,600 |
| Diagonal, 64 independent leaves | 0.0215 ms | 105,984 |
| Diagonal, four groups of 16 | 0.1267 ms | 221,696 |
| Diagonal, one group of 64 | 0.7233 ms | 800,256 |

The last timing ranged from 0.7181 to 0.7238 ms across the three runs. It excludes the first pose calculation, surface emission, lighting, GL calls and GPU work. At 60 calls per second, its measured allocation alone corresponds to approximately **45.8 MiB/s** for one 64-leaf assembly. That is an allocation-rate illustration, not measured garbage-collection pause time.

**Suggested improvement:** maintain an immutable runtime assembly snapshot containing validated members, UV bounds, outside direction, hinge/travel data and per-leaf static geometry. Share it among leaves and invalidate it on membership, configuration, orientation, block replacement and chunk lifecycle changes. Preserve the current fallback when part of a saved assembly is unloaded. A frame-local shared snapshot is a smaller first step, but needs invalidation for changes within that frame.

Then cache closed/open geometry and material clipping, transform reusable vertices for moving leaves, and investigate batching atlas-backed leaves. Moving all trapdoors into chunk meshes immediately would create animation/rebuild problems; caching assembly and geometry work should come first. Retain exact normals, UVs, Fit/Tile behavior and collision agreement.

## 2. Trapdoor redstone repeats group settlement for each recipient

Sources: [redstone channels](../../src/main/java/com/vandorlabs/redstone/RedstoneChannels.java), [trapdoor tile](../../src/main/java/com/vandorlabs/tiles/TileEntityProgrammableTrapdoor.java), [existing light batching](../../src/main/java/com/vandorlabs/blocks/ProgrammableLightConnections.java).

`RedstoneChannels.java`, `LoadedRedstonePower.java` and `SignalUpdateBatch.java` are unchanged from the 1.2 baseline. Channels remain per-world and loaded-only, with no periodic full-network scan. That is worth preserving.

The new trapdoor receiver bypasses the existing settlement optimization. `setChannelSignal()` immediately invokes `evaluatePower()`. Each changed recipient validates its group, reads group power and marks every member dirty. `requestOpen()` can validate the group again. Although channel notification already runs inside `SignalUpdateBatch`, trapdoors do not defer their derived work through `afterSignals()` as joined lights do.

For 64 leaves receiving one on/off pair, the probe measured:

| Layout | Regular leaves | Diagonal leaves | Allocated bytes per pair |
| --- | ---: | ---: | ---: |
| Independent | 0.0349 ms | 0.0391 ms | 118,272 |
| Four groups of 16 | 0.2716 ms | 0.3021 ms | 740,416 |
| One group of 64 | 1.2628 ms | 1.3413 ms | 2,768,736 |

These timings cover recipient callbacks, power reads and mock state changes. They **exclude channel reconciliation, real chunk updates, packets, sound delivery and lighting**, so they are not measured server tick times. Nevertheless, they demonstrate redundant CPU work and allocation before those additional costs occur.

Related burst paths:

- `configureGroup()` suppresses intermediate publication, but afterwards evaluates power once per leaf. Many setters also call `sync()` without checking whether the setting changed.
- `onLoad()` schedules repair/reconnection/registration/evaluation for each tile. Diagonal partial groups can rediscover the same component from multiple load callbacks.
- `evaluatePower()` marks all members dirty even when effective power is unchanged. Each actual open-state transition also emits a world event per leaf.
- Every leaf saves its full assembly list. A 64-member assembly duplicates 4,096 position entries across its tiles and full update tags. This is secondary to repeated computation, but adds allocation and packet/save work during group updates.

**Suggested improvement:** store incoming signals first, then settle each affected loaded assembly once at the end of the existing synchronous batch. Reuse its validated snapshot, compare old and new effective state, and update only changed members. Apply the same approach to configuration and deferred load batches. Preserve signal ordering, mixed local/channel power, inverted/disabled triggers and gear-cover interlocks; do not delay gameplay arbitrarily across ticks.

The older registry also reconciles every channel member on each input change and registration. Registering N members sequentially can accumulate O(N²) power reads. This is a pre-existing bottleneck that additional trapdoor members amplify. Batch registration/reconciliation per affected channel at the safe end-of-load point, but retain the full reconciliation semantics that prevent stale contributors from leaving channels powered.

## 3. Existing portholes and diagonal walls now do more CPU geometry work

Sources: [wall renderer](../../src/main/java/com/vandorlabs/client/TEAnimatedScreenSelector.java), [porthole mesh helper](../../src/main/java/com/vandorlabs/client/DiagonalPortholeMesh.java), [clipping implementation](../../src/portable/java/com/vandorlabs/render/DiagonalMeshClip.java), [neighbor bounds](../../src/main/java/com/vandorlabs/blocks/DiagonalNeighbourBounds.java).

The `c1512ea8` changes correct connection geometry and prevent clipping into occupied neighbors. They also add new work to rendering:

- Diagonal walls calculate flat-end transitions, covered ends and neighbor clipping bounds while rendering. `normalQuad()` clips generated polygons before submission.
- Diagonal portholes replace the earlier transform-based approach with per-polygon transformation, band splitting and clipping. The same preparation is reached in their opaque and translucent passes.
- **Flat portholes also take the new helper path.** With `mesh == null`, `DiagonalPortholeMesh.emit()` still clones each vertex, builds lists/arrays and calls `DiagonalMeshClip.quads(null, ...)`. The 1.2 `panelRect()`/`panelQuad()` emitted vertices directly. This is avoidable overhead in existing flat porthole builds, independent of the new diagonal features.

For a representative 64-panel batch emitting the same 512 POSITION_TEX vertices into a buffer:

| Emission path | Median CPU time | Range of run medians | Allocated bytes |
| --- | ---: | ---: | ---: |
| Reproduced 1.2 direct emission | 0.0062 ms | 0.0062–0.0069 ms | 1,536 |
| Current flat-porthole helper | 0.0170 ms | 0.0147–0.0291 ms | 120,320 |

This isolates one emission pattern, not the entire porthole renderer. Timing varies; the additional allocation is consistent. Real porthole frames contain multiple surface pieces, so the allocation repeats for each piece.

The clipping helper itself allocated 1,008 bytes for a quad wholly inside clear bounds, and 2,408 bytes for the probe's single-obstacle case. It currently allocates intermediate lists even when a plane clips nothing.

**Suggested improvements, in order:**

1. Restore direct emission for flat/non-clipped surfaces. Add all-inside/all-outside bounds tests before entering polygon clipping.
2. Cache the final static diagonal mesh by shape, fill, ends, neighbor obstacles and material layout. Keep lighting and camera transforms as live inputs.
3. Move opaque static wall geometry into chunk models, following the existing block/slab design. Preserve translucent ordering and shader-correct normals, with pixel comparisons before acceptance.

Light and porthole group caches already expire every world tick, even without topology changes. That policy predates 1.3, but the new diagonal discovery path adds candidate allocations and plane checks to each rebuild. A bounded cache invalidated by actual local changes would avoid periodic render-thread discovery. Simply removing the tick expiry without complete chunk/neighbor/configuration invalidation would be unsafe.

## 4. Collision and selection can cause lag away from the rendering bottleneck

Sources: [diagonal trapdoor collision](../../src/main/java/com/vandorlabs/blocks/BlockProgrammableDiagonalTrapdoor.java), [offset interaction search](../../src/main/java/com/vandorlabs/tiles/OffsetTrapdoorInteractions.java), [client selection hooks](../../src/main/java/com/vandorlabs/client/OffsetTrapdoorSelection.java), [controller hook](../../src/main/java/com/vandorlabs/client/OffsetTrapdoorController.java).

### Diagonal collision meshes

`addCollisionBoxToList()` generates 16 slices for a closed/sliding diagonal leaf and **16 × 16 = 256** slices for an open rotating leaf. Each slice constructs corner arrays and bounds before intersection filtering. Group-based opening-direction calculations can add more work for joined leaves.

For one unjoined leaf and a query covering the whole leaf:

| Collision generation | Median time | Allocated bytes |
| --- | ---: | ---: |
| Vanilla stone control | 0.178 µs | 144 |
| Vanilla trapdoor control | 0.123 µs | 184 |
| Closed diagonal trapdoor | 3.232 µs | 10,072 |
| Open rotating diagonal trapdoor | 59.367 µs | 242,960 |

These controls have much simpler geometry; the comparison identifies absolute work rather than equivalent functionality. Small real queries retain fewer boxes, but the generation loop still runs before filtering. Crowds of entities or repeated movement queries multiply this work on the server and client. More visible blocks alone do not necessarily increase collision workload; proximity and entity activity matter.

**Suggested improvement:** cache local collision slices for each discrete open/closed configuration and assembly revision. Reject using a coarse bound before generating/testing detailed slices, and reuse geometry rather than rebuilding arrays. The current collision code uses the endpoint block state, not the interpolated visual pose, so an endpoint cache can preserve its behavior. Simplifying slices requires dedicated gap/edge movement tests.

### Global searches, including scenes with no trapdoors

`OffsetTrapdoorSelection.updateTarget()` runs from render, client-tick END, the replacement controller's update, and input hooks. It has no nearby-offset-leaf early exit. Its ray traversal adds a **5 × 3 × 5** owner neighborhood per ray cell to a `HashSet`, then checks each unique position. A five-block axis-aligned ray from cell center visits six cells: 450 candidate `BlockPos` constructions and 150 unique owner positions.

The measured additional empty-world trace cost was **7.588 µs / 18,008 bytes** for that straight ray and **13.111 µs / 30,152 bytes** for a five-block diagonal ray. Vanilla's empty straight-ray control was 0.186 µs / 744 bytes. The new trace supplements vanilla picking. Its absolute time is modest in this fixture, but repeated allocations exist even when the player has never placed a trapdoor.

The common collision event also searches an expanded volume on each event, regardless of whether any relevant leaves are nearby. The empty player-sized query measured 0.891 µs / 2,552 bytes. This is a local-volume search, not a scan of every loaded block.

**Suggested improvement:** maintain a loaded-only spatial index of offset-capable leaves by covered chunk section/cell. Empty sections should return immediately. Query only indexed candidates and deduplicate repeated target calculations when the view, reach and relevant block state have not changed. Preserve the pre-input hook needed for correct held-click behavior, as well as entity obstruction and exact hit ordering.

## 5. Render distance increases the number of expensive tiles

In 1.2, diagonal walls inherited the normal tile-render distance limit of 4,096 squared blocks, approximately 64 blocks. `TileEntityAnimatedScreenSelector.getMaxRenderDistanceSquared()` now returns `Double.MAX_VALUE` for diagonal `BlockProgrammableWall` shapes. Regular and diagonal trapdoors also use unlimited tile distance, with a fixed **17 × 17 × 17** render bounding box per leaf.

This fixes disappearance of architectural geometry, but retains per-frame tile rendering over more of the loaded scene. The trapdoor bound allows leaves whose owning cells are outside the view to survive frustum testing more often than a tight bound would. Loaded/rendered chunks and the normal visibility machinery still constrain work; “unlimited” does not mean the entire world is rendered.

For a uniformly populated horizontal area, doubling the effective radius from 64 to 128 blocks can expose roughly four times the tiles before other visibility limits. This is a geometric illustration, not a measured multiplier.

**Suggested improvement:** preserve long-distance architectural visibility while moving static housing to chunk meshes. Compute tight conservative motion bounds from the actual leaf/group geometry instead of using the maximum-size cube everywhere. Test extreme hinges, sliders, offset covers and chunk boundaries before tightening bounds. Avoid silently restoring the old disappearance bug as a performance fix.

## 6. Material expansion adds memory pressure and first-use stalls

Sources: [atlas loader](../../src/main/java/com/vandorlabs/client/UnifiedTextureSprites.java), [filesystem catalog](../../src/main/java/com/vandorlabs/tiles/FilesystemTextures.java), [custom material resolution](../../src/main/java/com/vandorlabs/client/CustomBlockTextures.java), [screen renderer](../../src/main/java/com/vandorlabs/client/TEAnimatedScreenSelector.java).

The current catalog contains 227 extras beyond the legacy finishes. `UnifiedTextureSprites` registers entries at atlas stitch time, including static screen artwork and door views whether or not the world uses them. Custom `Sprite` loading pads each image to a power-of-two square. For example, each new 140×140 storage face occupies a 256×256 canvas.

Accounting against the current standard-build resources finds **247 custom Sprite entries, 29,851,648 padded pixels, and 113.875 MiB of base RGBA pixel payload**. A full mip-chain approximation raises that payload to 151.833 MiB. This excludes normally registered sprites, filesystem additions, atlas packing waste, temporary decoded images, other mods and shader textures. It is **not measured VRAM or the net 1.2-to-1.3 memory increase**; some source artwork existed previously in other rendering paths.

Filesystem discovery reads/decodes PNGs during initialization, and atlas loading reads them again. The 2048-pixel dimension check happens after image decoding; there is no aggregate folder budget. This primarily affects startup/reload and memory availability, rather than repeatedly reading files while looking at blocks.

Two other avoidable stalls/work paths deserve attention:

- The first custom-block texture lookup builds a table by walking every registered block and 16 metadata values. This happens lazily in a synchronized method. Subsequent TESR custom-material lookups can still resolve models and door quads rather than use cached sprite selections.
- The main screen/console rendering branch resolves and binds its selected animation/static texture **before** applying a static surface override. An animated underlying selection can therefore decode/upload an unused compact animation on first view. The `bindScreenSurface()` helper used by full inputs already has the earlier override check that the main branch needs.

**Suggested improvements:** account for atlas dimensions/heap/VRAM in a hardware profile; avoid unnecessarily large padded previews and redundant full/half representations where visual equivalence can be maintained; inspect PNG dimensions before full decode and provide an aggregate filesystem budget/diagnostic. Cache custom sprite resolution per model/resource-reload generation and move expensive first-use preparation to the appropriate load stage. Resolve a static screen override before loading or binding the unused animation.

## 7. What appears healthy, and smaller remaining risks

**Programmable Block, Slab and Stairs:** retain cached baked models and disabled tile-render passes. Per-face textures existed in 1.2; they are not a new sixfold per-frame cost. New side-texture keys and storage faces increase model-cache variety and chunk rebuild work, not steady-state Java submission for every visible cube. The housing cache uses individual face variants rather than caching every six-face combination. The new Fit/Tile `ScreenHousingMesh.sideLayout()` also caches fitted meshes.

**Programmable Storage:** uses the baked housing path, explicitly disables tile rendering, has no idle ticking or channel-load behavior, and excludes inventory contents from appearance packets. Large numbers still consume tile/inventory/save memory, and hoppers/comparators add activity-dependent work. A small avoidable allocation exists: `getUpdateTag()` calls the superclass implementation, which dispatches to storage's `writeToNBT()` and serializes inventory before removing `Items`. Write appearance-only data directly for appearance packets; preserve full save/container synchronization.

**Lights and screens:** joined-light signal settlement remains batched, and full Programmable Lights retain Forge's fast renderer. Frames/slabs are separate renderer paths, but were already separate in 1.2. The newly added `!isSmallInput()` check does not divert ordinary full light blocks to a slow path: small mode is restricted to Light Frames. Actual emission changes still trigger Minecraft light propagation and block updates; large pulsing installations remain a likely source of spikes, without evidence here of a new core-channel regression.

**Connected Duplifier:** discovery changed from 6 to 26 neighbors while retaining the 4,096-cell limit. At that limit, accepted cells enqueue up to 106,496 neighbor candidates versus 24,576 before deduplication. Applying many settings still runs synchronously and can trigger packets, light work and chunk rebuilds. This is an edit-time stutter risk, not idle rendering cost. Deduplicate before queueing, reuse captured configuration where possible and batch derived notifications while preserving atomic discovery, permissions and loaded-only behavior.

**Landing gear:** cover refresh searches 150 cells at configuration/completion; the new calls do not run on every moving tick. Gear already ticked before this range. Extra Large adds geometry/reservations, but is a lower priority than trapdoor groups unless profiling a gear-heavy build.

**Existing displays, glass, chairs, engines and active ramps:** texture switches, translucent overdraw, geometry complexity, particles and motion can still dominate particular scenes. The relevant unchanged paths are existing bottlenecks rather than demonstrated regressions since 1.2. Catalog/picker changes should not be blamed for a universal per-block idle tick: most programmable tiles, including the new trapdoors and storage, do not implement `ITickable`.

## Validation plan for improvements

First preserve the current behavior and measure changes on the same scenes. Use the existing [render benchmark](../../src/main/java/com/vandorlabs/client/ProgrammableRenderBenchmark.java) and [redstone benchmark](../../src/main/java/com/vandorlabs/client/ProgrammableRedstoneBenchmark.java) as starting points. Their default 16/64 registry fixtures and screen/light pulse tests do not cover large trapdoor groups, global picking/collision hooks, real frame tails, texture pressure or trapdoor channel settlement. Older CSVs elsewhere in this directory predate 1.2 and must not be relabeled as this comparison's baseline.

| Workload | Cases to compare | Evidence to collect |
| --- | --- | --- |
| Common 1.2 scenes | Cubes/slabs/stairs, flat/diagonal portholes, diagonal walls, lights and screens; identical saved settings | 1.2/current frame p50/p95/p99, allocation and chunk rebuild time |
| Trapdoor rendering | 64/256/1,024 total leaves; independent, 8-, 16- and 64-member groups; regular/diagonal; stationary/moving | CPU renderer time, draw calls, allocation, group-cache misses and images |
| Visibility | Same dense scene at 32/64/128/256-block viewpoints, stable render distance | Actual submitted tile counts and hardware CPU/GPU frame times |
| Redstone | Physical and virtual edges; mixed channels; normal/inverted/disabled; 64/256/1,024 recipients | Server tick p95/p99, settlements per group, power reads, packets and lighting time |
| Loading/editing | Chunk-boundary groups, reloads, repeated configuration and 4,096-cell copies | Main-thread stall duration, allocations, dirty chunks and packet counts |
| Collision/picking | No leaves nearby, individual leaves, open groups, moving player plus increasing entity counts | Query counts/time/allocation; correct nearest hit and collision behavior |
| Resources | Default assets, many custom samples, bounded/large filesystem folders, reload and first view | Atlas dimensions, peak heap, VRAM, upload/decode stalls and reload correctness |

Run hardware trials without shaders and with the owner's shader/mod configuration separately. A software-renderer result can help compare CPU submission paths but cannot establish hardware FPS or shader acceptance. Keep vanilla stone/slab/trapdoor/lamp controls and distinguish geometry differences. Do not assume linear scaling or infer p99 frame time from these microbenchmarks.

For implementation changes, use Java 8, the relevant non-rendering checks and the live client suite. Include visual comparisons for diagonal joins, filled faces, flat portholes, normals, transparency, materials and trapdoor motion. Cache tests must cover unload/reload, partial groups, resource reload, copied settings and block replacement. Keep all traversal loaded-only.

## Reproducing this review's diagnostics

Evidence: [probe source](1.2-to-1.3/PerformanceProbe.java), [Gradle init script](1.2-to-1.3/probe.gradle), [run 1](1.2-to-1.3/probe-1.csv), [run 2](1.2-to-1.3/probe-2.csv), [run 3](1.2-to-1.3/probe-3.csv), [texture accounting](1.2-to-1.3/texture-budget.py).

Machine: AMD Ryzen 7 9700X; OpenJDK 1.8.0_504, 64-bit Server VM. Each probe JVM used a 512 MiB heap, 1,000 warmup operations per case and 21 samples of 100 operations. Tables show the median of the three run medians and median allocation values. Runs were sequential. CSV p95 values describe amortized sample times, **not individual frame/tick percentiles**. Some small timings show JIT/scheduling variation, notably the flat-emission path and eight-member group validation.

The map-backed world treats chunks as loaded and suppresses real notifications, dirty-chunk bookkeeping and sounds. It retains block/tile state and calls real group, geometry, collision and signal methods. Assembly lists are populated outside timing to isolate steady work. The signal probe delivers recipient callbacks directly in a fixed order; it does not simulate the full channel registry. The collision query covers an entire leaf. All allocation counters measure only the executing thread's Java heap; native buffers/driver allocations are excluded.

From the repository root:

```bash
git log --oneline 0b8ac9dd..d24338e4
git diff 0b8ac9dd..d24338e4 -- src/main/java src/portable/java
JAVA_HOME=/usr/lib/jvm/java-8-openjdk-amd64 ./gradlew --no-daemon \
  -I docs/performance/1.2-to-1.3/probe.gradle performanceReportProbe
python3 docs/performance/1.2-to-1.3/texture-budget.py
```

The probe task compiles classes/resources and diagnostic classes; it does not build or copy a release JAR. All three retained probe runs completed successfully. This review identifies concrete optimization targets, but does not establish an overall percentage slowdown between releases.
