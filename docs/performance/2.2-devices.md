# Version 2.2 device rendering

Landing gear uses one renderer at each complete assembly root. Member blocks do
not each submit the entire assembly. Native meshes and atlas UVs are decoded once
per resource reload. Stationary world assemblies reuse transformed vertices,
including directional shading, with a maximum of 64 transforms per mesh. World
position and light are applied during each draw. Resource reload discards the
cache. Arms in motion and wheels on vehicles use the continuous transform path;
there is no angle quantization or lower animation tick rate.

The three constructor designs use one Forge FastTESR at the Core, sharing Forge's
batch buffer. Reserved cells do not render the model again. Complete OBJ meshes
are baked once per reload, and each horizontal orientation is prepared once.
Constructor Cores have no tick callback. Reserved cells still validate their
owner once per second so orphaned reservations can recover safely.

Gear ownership checks use cached members once per second; ordinary rendering
does not flood-fill the assembly. Moving gear still checks its swept collision
and pushes entities. These gameplay checks remain separate from render caches.

The native client suite compares the original and cached vertex emission for all
18 size/arm/foot combinations (Mount, Extender and Swing Arm; standard and Large;
Plate, Ski and Wheel), testing both endpoints and the midpoint of moving arms.
It also checks each constructor in all four horizontal facings. Positions must
agree within 0.00001 blocks; color, UV and light fields must match exactly.

The CPU microbenchmark renders 16 copies into a reused BufferBuilder, alternates
reference/cached order, warms up 15 times and records 31 samples. It measures
vertex submission and Java allocations, excluding OpenGL upload, GPU execution,
world simulation and frame scheduling. These measurements do not predict FPS.
Live screenshots, wheel-motion checks and deployment GIFs provide separate
visual validation.


## Measured CPU submission

| Cases | Reference sum of medians | Cached sum of medians | Reduction |
| --- | ---: | ---: | ---: |
| 30 stationary gear poses | 8.612 ms | 7.382 ms | 14.3% |
| 12 moving gear poses | 3.207 ms | 3.205 ms | 0.1% |
| 12 constructor/facing combinations | 2.184 ms | 1.953 ms | 10.6% |

Each row sums the per-case medians for batches of 16 copies; it is not one frame
containing all those devices. [Individual timings and allocation counts](2.2-devices.csv)
include p95 values. Small cases vary, and some do not improve. Moving gear uses
the same continuous vertex path and shows effectively unchanged timings.
The shared stationary gear cache held 304,416 bytes of vertex arrays after the
54 cases, excluding map/object overhead. Its per-mesh limit bounds retained poses.

## Packaged artwork

The standard JAR now stores 751 PNGs instead of 895. A compact manifest preserves
144 old resource paths through a default fallback pack; user texture-pack overrides
remain higher priority. Dynmap references point directly at the retained files.
All 895 previous PNG paths were compared against the new package: every decoded
RGBA byte and image dimension matched. The live client also checked aliases at
startup, after a resource reload, and beneath an overriding resource pack.

Lossless PNG compression improved 738 staged images. PNG ZIP payload fell from
12,271,935 to 9,601,764 bytes after compression and deduplication, a 21.8% reduction.
The complete standard JAR fell from approximately 30.34 MB to 27.65 MB. Turntable
masters, UV atlases, item artwork and other textures keep their intended resolution;
the separate screen-animation payload is unchanged.

Compatibility paths can still occupy separate atlas sprites when both names are
requested. The PNG packaging measurements describe disk/download size; GPU atlas
memory and texture startup time were not measured.
