# Vehicle performance follow-up in 2.8

This follow-up investigates the first three priorities in the [2.8 performance summary](2.8-summary.md): carried rendering, terrain/prediction allocation and conversion preparation. Measurements use a copied previous-version vehicle with 3,325 captured blocks and 3,032 tile entities. Tile count is not a count of individual draw calls: plain programmable blocks already use retained block meshes, and eligible opaque walls share batches.

## Changes

- Terrain gathers reuse a scratch open-addressed set and packed primitive section keys within one synchronous physics/reconciliation batch. A later batch reads the world again. Foreign bounding-box subclasses retain an isolated gather and their virtual offset calls.
- Collision clipping and turning translate ordinary obstacle coordinates directly instead of allocating a translated bounding box for each hull/obstacle pair. The reference path remains available to the benchmark.
- One transfer reuses the validated immutable snapshot/view across asynchronous journal preparation. Live source, permission, security and hardness checks still run. Changed block hardness after durable journal preparation is refused without removing source blocks.
- Scans share up to four two-millisecond work slices per world tick. A lone scan can consume otherwise unused slices; unfinished jobs rotate behind other jobs. The aggregate target remains eight milliseconds, with timeouts counted once per world tick. A single indivisible callback can exceed this target.
- Optional benchmark instrumentation separates main and shadow vehicle submissions and groups individual tile renderers by tile class. It records submission time, including driver waits; it does not measure GPU execution time.

Vehicle weight estimation is included in the candidate scan. It reuses the scan's validation view and processes bounded inventory work in slices. It neither adds a per-driving-tick cargo scan nor changes movement.

## Measurement conditions

The before/after runs use the same saved-world source, Java 8, full optional-mod pack, OptiFine G5, Complementary Unbound 5.6.1, six-chunk distance, camera paths and 12 GiB heap. JFR profile recording is enabled in both runs with a 96-frame stack limit. Each stationary camera samples 60 completed frames after warm-up; moving Taxi samples 180 frames with authoritative travel checked. Rendering uses Mesa llvmpipe, so these are software-rendered comparisons, not hardware FPS estimates.

Terrain comparisons additionally compare reference and optimized paths against the same loaded craft. Six poses cover three headings and forward/reverse movement, with displacement required to agree within 1e-9. Allocation counts use the server thread's ThreadMXBean rather than sampled allocation attribution.

## Results

The shared collection change reduces allocation from 1,110,516 to 1,030,745 bytes per physics step (averaged across six poses) (7.2%). The same test's median CPU time changes from 2,829 to 2,784 microseconds. Terrain-query counts and displacement agree. Avoiding translated obstacle objects changes measured allocation by only about 4.8 KB per step, with no CPU improvement established; this is consistent with the JVM already eliminating much of that temporary allocation.

The complete scan falls from 110 world ticks to 39, including the newly added weight pass. The candidate performs 108 slices and 708 ms of measured scan work; its heaviest tick contributes 124 ms. One immutable transfer validation view is built and reused after asynchronous journal preparation. This shortens waiting and removes duplicated preparation, but does not establish an eight-millisecond maximum conversion tick.

Both native controls also change between runs, and render-thread CPU time increases. These whole-scene differences do not establish a rendering/FPS improvement from the terrain changes. Render-thread allocation is not reduced by this round. Physics allocations are measured separately; the render event does not include all client prediction work.

In the stopped scene, carried submission averages 1.88 ms in the main pass and 17.26 ms in shadows. Shadow work includes block meshes (3.73 ms), opaque wall batches (2.97 ms), general screen tiles (3.33 ms), ramps (1.95 ms), doors (1.89 ms) and lights (1.08 ms). Storage cubes contribute only 0.65 ms across 100 shadow submissions. These figures include driver waits, and the whole-vehicle row includes the family rows. Expanding storage caching would have a small ceiling in this fixture; it would not explain the remaining full shader-frame cost.

## Remaining costs and next work

The baseline moving window contains 801 client-thread execution/native samples. Among 306 samples ending in `nglDrawArrays`, 249 are in world shadow rendering, 40 in world main/other rendering and 17 in carried vehicle meshes. Terrain gathering is the nearest Vandor method in 228 samples. This supports reducing terrain work and separating world/shadow costs before expanding vehicle tile caches. These sample counts are not GPU-time percentages.

The next useful preparation work is to make connectivity/grouping and synthetic view construction resumable, then reduce or defer encoding. Keep third-party tile construction on the server thread, retain whole-snapshot validation and test previous-version capability NBT. The remaining terrain allocation is largely the physical world's collision candidates; any reuse beyond one synchronous batch needs complete invalidation for changed blocks and moving owners. For rendering, obtain hardware GPU captures of world shadows and post-processing before treating the vehicle's tile count as the dominant cost.

The atomic native-block removal, lighting and neighbour phase still needs special treatment. The baseline measured 177 ms for this phase; the candidate measured 204 ms. This phase is unchanged, and no improvement is established. Spreading block/inventory publication across ticks requires corresponding durable partial-save recovery; simply yielding midway would weaken ownership guarantees. Continue slicing pure preparation first, and profile parent-world chunk/light work separately from journal I/O.

## Validation

The scalar obstacle checks compare 150,000 exact clipping results and 10,000 intersections with the translated-object path, including far negative coordinates, contacts, tiny movement and foreign offset overrides. Live Taxi checks cover ordinary entry, protection refusal, parking rollback and retry. Design checks exercise actual asynchronous preparation, immutable preflight reuse, post-journal hardness refusal, exact chips, retained-card authorization, cargo weight and parking. Dedicated-server linkage checks cover the changed shared code.

Weight checks include stack quantities, adjacent chest halves, nested shulkers, filled buckets, joined Hex Tanks, shared handlers, installed Mekanism bins/tanks and bounded unknown inventories. A formed Dynamic Tank is weighed and converted through all four cardinal headings with its shared fluid/inventory cache counted once.

## Chip displays and larger Surface areas

Vehicle shape previews previously walked the full 12×12×12 occupancy grid and emitted exposed faces on every rendered frame. They now compile immutable position/colour geometry once and rotate the retained mesh. The cache has an 8 MiB vertex-payload budget and a 128-entry bound, and releases graphics resources on resource reload and world unload. A focused rendered check performs 100 additional rotations without rebuilding a mesh. Playback uses a pause-aware client clock; Slow, Normal and Fast preserve phase when changed.

Joined Chip screens submit one canvas for a complete artwork rectangle, including a 2×2 display with its only reader attached to a non-owner panel. Repeating 400 member lookups does not rediscover the group. Block/render updates and carried-tile revisions invalidate the lookup; world references do not retain discarded synthetic vehicle worlds. Company Master Chip logos use a fixed metadata lookup rather than searching the texture catalog every frame.

Programmable Surface areas now allow 32 blocks on each side: up to 1,024 cells. Copy Controllers accept matching filled rectangles; Turntables retain square pads. Screen artwork groups allow up to 4,096 connected cells, matching the existing programmable-block plane bound. These limits remain finite because scans, topology publication and volume checks grow with area. Payload, height, item/NBT and capture limits remain separate. Turntables reject captures above 4,096 occupied blocks before transfer, including on a larger pad.

Two focused runs measured loaded-pad discovery with 15 samples per size:

| Pad | Cells | Median in first run | Median in second run |
| --- | ---: | ---: | ---: |
| 16×16 | 256 | 119 µs | 64 µs |
| 32×32 | 1,024 | 369 µs | 452 µs |

These measurements cover traversal and layout construction on already loaded chunks. They exclude placement notifications, chunk loading, inventory serialization and transaction publication. They support a bounded increase, not a claim that larger builds are free. Variable-size Surface artwork meshes also have an 8 MiB estimated retention budget rather than relying only on an entry count.

The next useful measurements are hardware main/shadow-pass timings for populated screens and font rendering, followed by edit/reload bursts on large Surface pads. The earlier shader-scene findings above still apply: software render checks, fewer geometry builds and local scan timings do not establish hardware FPS. Equivalent chip copies could also share preview geometry by content if profiling shows significant repeated mesh preparation or cache churn across many distinct chips.
