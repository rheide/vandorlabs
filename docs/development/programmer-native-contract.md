# Card / Chip Programmer conversion contract

The released block and shared inventory owner both use `data_chip_programmer`. Four reserved cells form a two-wide, two-high console, with one controller at part zero. Horizontal facing and part occupy the original four metadata bits. The native family remains inactive while source references and portable adapters are prepared.

The physical inventory has three slots, each limited to one item: Master, Input and Output. Company cards or non-Journal, non-Vehicle company Master Data Chips authorize the Master slot. Input and Output accept valid Access Cards or Data Chips with companies zero through six. Invalid saved stacks are not permission to discard their original ownership data.

Program consumes the sole Input, producing one Output and retaining Master. A selected company Master rebrands the result; otherwise the existing nonzero company remains. Journal programming edits bounded plain text, preserving unrelated item data. Copy requires one matching base item in each of Input and Output, then replaces the existing Output from the complete committed Input. It neither consumes Input nor commits the editor's draft. A missing or incompatible material item refuses the operation.

The first actual source corpus freezes 21,904 descriptor/authorization decisions and 392 programming/copy results, including exact retained item NBT, draft state and writing status. Its SHA-256 is `ef75c4ffecd2e1b4c7b4ce4fb50c4bbf6894dc8ccd51e3202e2342e7476a9ce2`. The fresh save contains three empty slots, false Journal mode, an empty title, eight empty entries and zero Writing/Complete counters. Titles are bounded to 40 characters and each entry to 512 characters. Successful operations enter 20 ticks of Writing, then 60 ticks of Complete.

Draft, Program and Copy retain wire operation indices zero, one and two. Vehicle draft/program indices three and four remain unavailable in native conversion; imported Vehicle envelopes remain opaque and must not be destructively reprogrammed through ordinary actions. The later host will reuse the shared inventory-item decoder and credential/journal codecs rather than introduce independent ownership decoding.

Controller lifecycle, four-cell placement rollback, mining/recovery, authorization through real menus, authored models, resource overrides, item padding and pause-aware visual status require subsequent focused references and acceptance before activation. There is no native registration or global client binding in this foundation checkpoint.

The portable policy contains descriptor decisions only; the released tile keeps its existing inventory mutations and delegates validation to that policy. The unchanged source corpus is paired with dedicated-server linkage and a programmer-only live focus, which exercises actual sockets in four facings, bounded program/copy packets, journal Previous/Next interactions and occlusion, draft isolation, dedicated editor widgets, four rendered status meshes, retained-token negative controls and inventory padding. The focus excludes the surrounding utility and Vehicle gameplay matrices.

The inactive native foundation supplies `NativeProgrammerDraft` and `NativeProgrammerRules`. Drafts expose immutable bounded entries and preserve unrelated fields when writing their own known keys. Rules reuse the portable policy, shared inventory decoder, credential company components and existing Journal writer. Their result methods return defensive copies; they do not consume, replace or publish any physical slot. The future host remains responsible for the single authoritative ownership transaction.

Dedicated native replay matches all 21,904 source decisions and 392 operation results, checking result company/type/count and Journal content, unchanged source/master/material owners, and preservation of the complete original import envelope. Sixteen current/imported chip-type combinations establish type precedence and refusal of unavailable Vehicle mutation without touching retained bytes. The shared `NativeChipJournal.vehicle` predicate uses the same existing payload precedence as Journal display. No programmer block, entity, menu or network registration is added.

The source placement corpus adds 816 actual vanilla ItemBlock-use and callback failure cases, with all 16 metadata states. It captures obstructed/denied cells, unloaded-cell callback preflight, individual failed writes, rollback, material consumption and the source exclusion of item BlockEntityTag from installed inventory. Its frozen SHA-256 is `181d5e24ec4ab4ecc06e6613f1097a3eb7e5b3c280a6220d64d274e152f9a5fe`. Normal collision and outline are full cubes in each reserved cell; selection rays instead intersect the authored triangles.

Actual source property getters report hardness 3.5, explosion resistance 3.5, default stone sound, no explicit harvest tool/level, required tools and successful wooden/stone pickaxe harvesting. These values must not be inferred from other Iron families.

The source artwork reference bakes all 20 manifest parts with Forge's OBJ loader, then invokes the released batched emitter for 512 status/facing/card-mask/alpha/light profiles, totaling 239,616 vertices. It also captures the actual ProgrammerItemModel quads and transforms, atlas extents and buffer-translation reset. The unchanged Java 8 `ProgrammerTransform` and `ProgrammerStatus` are now portable sources shared by both platforms. `NativeProgrammerLayout` derives immutable cached four-cell offsets and minimum-corner render origins from that same transform, preserving all 16 source metadata combinations. Source placement/artwork goldens remain unchanged after the move. The native foundation replay also consumes the shared exact EMPTY item path directly and verifies every recorded metadata/cell offset. Upper-only visibility across render-section boundaries remains an explicit later actual-client case; an expanded bounding box alone is not sufficient evidence.

The inventory corpus freezes 1,800 actual IInventory/Forge InvWrapper operations, 1,680 socket/permission profiles and 86 timer samples. Its SHA-256 is `488ea87cd420cc0f0520ed3e1f21d54d44ac393d240743099698485ae8b3f678`. Direct setters retain their passed stack identity and clamp to one; slot validation remains a separate menu/automation check. Sockets always split one held credential, including Creative players, and empty-hand removal returns the sole existing item. Invalid or occupied socket clicks are consumed without changing ownership. Dead, spectator, distant, edit-denied, stale-owner and unloaded cases refuse.

The status trace reaches Complete at authoritative tick 20 with 60 ticks remaining and Ready at tick 80. Client tiles do not decrement those counters; status textures are static and change on authoritative phase updates. Later pause/lag/repeated-update checks must retain that boundary rather than predict a new phase before its server update.

Saved-state staging is checked against 3,528 actual source loads, with SHA-256 `c9fab72182445314cc7f6999ac818f586df26e733ad50ebdfef59335c5a19de3`. `NativeProgrammerSnapshot` prepares all three slots locally through the shared inventory decoder, then exposes defensive copies and an immutable draft. It normalizes the same saved text and phase counters, and writes one explicitly versioned inventory while preserving unrelated fields. It neither installs platform state nor publishes a block or inventory.

Ambiguous duplicate/out-of-range slots, unsupported item/count/company data, public/recovery projections, unavailable Vehicle state and unsupported block capability/component envelopes refuse staging without changing the original input. Known credential import wrappers, including opaque item capability bytes, remain intact for single-owner transfers. The eventual host must guard actual superclass/attachment installation and retain the original snapshot on any failure; these pure tests do not establish live host recovery or item publication.
