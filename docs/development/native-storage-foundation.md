# Programmable Storage foundation

Programmable Storage is an independent 27-slot inventory. Adjacent blocks do not merge. It exposes the same inventory through the item-handler capability on every face, uses the vanilla chest menu and comparator calculation, and emits no block light. Its Source subclass suppresses inherited deferred redstone-channel behavior; shared Screen defaults and services must not be installed as Storage behavior.

## Released behavior reference

`exportStorageSourceReference` invokes the actual Source block, tile, item, inventory wrapper, chest transfer, configured pick/drop, appearance-copy and Configurizer callbacks. The bounded reference contains 39 typed/repeated snapshot reads, 180 inventory operations, 36 automation profiles, 252 comparator profiles, 192 actual configured ItemBlock placements, 48 ordinary block activation profiles, eight Configurizer event callbacks, 32 metadata decodes and fourteen Storage artwork sets. The reference SHA-256 is `02a04c006aa4211dff586fa6fcaf8dae05f5d2eefbeb8cab3291feb265938fe5`.

These are actual callback and vanilla implementation observations in memory worlds, not live player packets. The test initializes the real Forge item-handler capability. Its Configurizer event subclass supplies the declared cancelability normally installed by Forge transformation; the actual handler performs the routing.

A fresh Source factory selects Cabinet at choice 295. Reading an empty or incorrectly typed old housing snapshot first inserts that default, then applies the unversioned palette migration, producing 294. Actual item placement merges settings into a freshly saved, versioned tile and therefore retains 295 when the item does not specify a housing. Factory defaults and old-snapshot decoding are intentionally separate.

Missing or incorrectly typed `Items` does not clear an existing inventory. A present list clears it before loading; a list with the wrong element type therefore leaves it empty. Duplicate slot records use the later entry. Invalid slots and unknown item IDs are discarded by the released vanilla decoder. The native ownership boundary must retain and refuse unsupported inventory snapshots rather than silently losing their bytes.

Configured drops, pick-block and copied item settings exclude `Items`. Breaking the block ejects the inventory separately and empties its old slots. Applying appearance settings preserves the target inventory. A disabled face-override source also preserves the target's stored face choices. Storage inheritance uses each set's matching front, side and top artwork; explicit face overrides use the selected front artwork.

Ordinary main-hand activation opens inventory. Creative sneak activation and the Configurizer use the shared material configuration path. Offhand activation is refused. Inventory usability requires the installed tile identity and distance at most eight blocks. The native adapter will reuse existing housing settings, material picker and configuration authorization, with a separate inventory codec and no public registry hooks until private ownership and saved-world checks pass.

## Item envelope staging

The separate `exportStorageItemSourceReference` records eighteen actual Source item envelopes and all 411 vanilla item IDs, including a filled shulker item produced by the released block's real break callback. That payload has no nested block-entity `id`; inferring the known vanilla container type from its item identity is necessary. Source's actual registered vanilla data fixer reports version 1343. The item reference SHA-256 is `0ce7e9b5070cb03dfa7c01a6274e2877eaa9bbcdc30084f22f9279a0a360bc62`.

`NativeInventoryItems` stages vanilla items with the platform's real item-stack DataFixers and registry-aware codec. Its narrow container preflight checks known ownership envelopes before conversion. Unknown positive-count items, nonempty item-level or nested block-level `ForgeCaps`, and unknown nested inventory fields are refused without modifying the input. Opaque capability data is not traversed. Proven credential imports use the existing credential adapter. An empty count must not erase an opaque capability owner either. Tagged legacy mod items and non-container block/entity payloads require their own proven adapter. The Source vanilla-ID manifest is checked before DFU, so a nonexistent old ID cannot become a newly registered modern item. Known container children are staged first and removed from the parent's DFU input, then installed through the native container component; vanilla DFU therefore cannot reprocess a credential child or discard its opaque payload.

The dedicated `test_storage_codec.py` focus exercises damage, names, lore, enchantments through the real dynamic registry, written books, nested chest contents and the actual filled shulker drop. Unknown nested owners are refused. Bounds apply to nested item count and container depth; the helper retains no world or rendering cache. This stage does not yet publish an inventory or implement host placement/mining recovery.

The shared helper is `com.vandorlabs.neoforge.inventory.NativeInventoryItems`, also available to the inactive Programmer adapter. Its `legacy`, `modern` and `write` methods are world-free; optional shared budgets bound an entire staged inventory. The real dedicated codec focus passes 71 assertions across eleven supported and seven refused Source envelopes plus adversarial native ownership/depth cases. Retained negative checks exposed zero-count capability erasure and acceptance of a modern-only vanilla ID before the corresponding guards were added. All disposable server runtimes are finalized through the shared retention helper.

## Complete slot staging

`NativeStorageInventory` returns a separate, fixed 27-slot result and never changes the previous owner during decoding. Native saves write schema 1, the current item data version and a complete `Items` list, including an explicit empty envelope. Future or incomplete native schemas are refused. Legacy missing or wrongly typed top-level `Items` preserves the previous slots; a present list replaces them, matching the frozen repeated-read cases. Unsupported positive-count out-of-range entries are retained through refusal rather than silently discarded.

The dedicated codec focus additionally passes all 33 supported snapshot reads and refuses six ownership-bearing snapshots, including a late-slot failure that must not publish an earlier decoded prefix. Native round trips cover every slot. The combined item and inventory codec checks pass 1,952 assertions; the runner requires both phase markers before retirement.

Bare Source `ItemStack.EMPTY` descriptors serialize as `{id:"minecraft:air",Count:1b,Damage:0s}`. The shared helper recognizes only that proven empty shape after ownership guards; it does not discard nonempty tags, unknown fields or capabilities. Native empty `{}` also round-trips through the helper. Normal saved inventories still omit empty slots.

## Inactive placed owner and item transaction

`NativeStorageEntity` is an independent `Container` with the vanilla three-row chest menu and item-handler wrapper. It stages all slots before installing a loaded snapshot. Its immutable housing/model update contains no inventory or retained private data. Inventory mutations update a cached vanilla comparator value without rebuilding the appearance projection; housing edits use the shared configuration authorization and avoid inventory serialization/scans. Local `onLoad` only queues identity-checked, loaded-only comparator notifications.

The block and specialized item remain unregistered. Placement uses `NativeStationaryPlacement`: decoded choices and inventory precede observers and consumption. Unsupported item ownership is refused before mutation. An installation failure restores the old cell without consumption; a refused rollback retains one consumed, inert recovery owner. Such recovery items cannot be placed. This checks caught failures and a complete saved-world restart, not abrupt termination or partial cross-chunk saves.

Configured pick and normal block drops exclude inventory. Actual mining ejects normal contents separately, including Creative and wrong-tool removal. Failed snapshots instead produce exactly one private recovery item in all four Creative/Survival and correct/wrong-tool combinations. Creative pick of a failed owner remains inventory-free. If a failed partial load omitted `Items`, its incoming opaque snapshot and the former usable inventory are quarantined together in one private, unplaceable owner. Appearance-only rereads cannot erase that quarantine or reactivate its slots. Nonempty block-level `ForgeCaps` is refused separately from each item's capability envelope.

The private `test_storage_host.py` dedicated focus passes 2,078 write checks and four complete-process restart checks. It replays all 252 released comparator profiles, 180 inventory operations, 36 automation profiles and all typed/repeated inventory snapshots. It additionally exercises the actual registered item capability, vanilla chest quick-move in both directions, all-slot publication ordering, private-update/pick boundaries, real `ServerPlayerGameMode` placement/mining, late-slot refusal, rollback faults, stale unloaded capability access and specific cold-neighbor boundaries. This uses server-side test players, not a live client packet or renderer. The runtime is retired only after both processes, retaining logs and class/reference hashes.

The dedicated material dialog now has opt-in bindings, as described below. Public registry, capability registration, client model/material rendering and canonical live-client acceptance remain prerequisites for activation. Storage receives no Screen channel service or embedded-reader implementation.

## Ambiguous duplicate ownership

A separate eight-case actual Source Storage/`ItemStackHelper` reference preserves the original corpus hashes. It demonstrates released last-wins behavior for plain duplicate slots, nested plain items and an empty container. It also records how that normalization can overwrite an earlier credential envelope or filled container. The separate reference SHA-256 is `76e8b0405d1141d06bceb4bdee966914eddb55ac3f0396c76e91201de2b70e83`.

The native decoder preserves ordinary vanilla last-wins behavior. An ambiguous duplicate involving a credential or nonempty container is instead refused, retaining the entire original owner. This safeguard applies both to Storage slots and to legacy nested container slots; otherwise a child credential could disappear before the parent is inspected. Native container duplicates are refused outright because native writers do not emit them. `NativeInventoryItems.ownershipBearing` exposes this narrow world-free distinction for other staged inventories. Empty containers do not count as nested physical ownership.

An actual placed-owner negative reproduced the earlier opaque-credential loss before the guard. The same focus now replays the Source duplicate reference and retains refused originals exactly, including opaque capability bytes, while the ordinary duplicate controls still match Source. This is intentional recovery behavior for ambiguous snapshots rather than a change to released Source production code.

Here `ownershipBearing` means a nonempty Access Card or Data Chip, or a stack with a nonempty container, bundle or charged-projectile component. It does not classify an empty container or ordinary scalar stack as nested ownership. The final dedicated host replay passes 2,089 write checks and four restart checks; the existing shared item/inventory codec focus still passes 1,952 assertions. Both complete runtimes are pruned through the shared helper after their final phase.

## Dedicated material editor

Storage's material dialog reuses `ProgrammableBlockDialog` and `NativeMaterialPicker`; ordinary inventory access continues to use the vanilla chest screen. The separate actual Source `GuiProgrammableWall.initGui` reference freezes 48 layouts across both viewport sizes, texture layouts, face-override states and every face target. Its SHA-256 is `82e538c1f6c4294887dcdddea6290ea5a777178c7cd25e3b2d32332c714386fc`. The headless oracle installs an empty localization table, so the Done label is compared as a localization key. It does not draw a Source window.

`NativeStorageMenu` binds edits to the exact installed owner and current window. Every edit rechecks the current held Configurizer or Creative permission, loaded identity, range and edit authorization. The fixed settings body is 42 bytes including position, window and six face choices; it never accepts inventory or arbitrary NBT. Length and scalar checks precede face-array allocation. Layout/face changes preserve the stored side material, all slots and unrelated private state. A face/main edit also preserves a legacy side-layout flag when the effective layout did not change, matching the released setter's no-op behavior. The dedicated opener is shared by Configurizer and Creative sneak interaction.

The private dedicated focus passes 781 editor assertions in addition to the 2,089 owner assertions and four restart assertions. It compares all Source controls/list bounds, validates codec round trips and malformed input, rejects stale/replaced owners and wrong tools/windows, and exercises the block's actual GameMode routing with a test menu-provider adapter. That adapter intentionally replaces FakePlayer's no-op menu methods; it does not establish client networking.

The separate private client focus establishes the actual player path: 55 checks cover synchronized Survival mode, selected slot, both hands and position before opening; real native menu/widgets and material-row selection; wheel and scrollbar drag; previous-value right click; settings C2S/S2C; rejected packets after tool removal or window closure; and ordinary vanilla inventory opening with the seven saved diamonds in slot 26. The server also verifies independent adjacent inventory and unchanged private ownership. The 42-byte figure is the settings body, excluding Minecraft framing and fixture acknowledgements.

Bindings remain explicit: a block overrides `menuType()`, the chosen menu factory constructs `NativeStorageMenu(type, window, inventory, buffer.readBlockPos())`, `StorageSettingsPayload.register` installs the transport, and `NativeStorageScreen.register` installs its client screen. None is wired into public Bootstrap. The private world uses a fixture block without a production housing model; this UI proof does not establish Storage rendering, production translations or canonical registry/item acceptance. Runtime retention waits for both JVMs to exit and the server save to complete.

## Placement envelope completeness

A supplied native inventory envelope must include its schema, item data version and `Items` list before it is merged into a fresh placement draft. Missing fields must not borrow the draft's empty inventory or current version. An actual negative reproduced that acceptance before the preflight guard. Nine dedicated checks now refuse each incomplete form without changing the cell, consuming the held item or normalizing its private data. Complete explicit empty native envelopes remain valid; unmarked Source items retain their distinct missing/wrong-type `Items` factory behavior. The complete focused write/restart suite passes with this guard.

## Released world-model reference

`exportStorageModelSourceReference` invokes the actual `ProgrammableHousingModel` with its Storage flag and actual Storage block states. Its immutable reference covers 23,040 profiles and 41,472 emitted quads: fourteen Storage sets plus two ordinary materials, four horizontal facings, three texture layouts, inherited/mixed/dormant face overrides, ten visibility masks and square/portrait/landscape sprite aspects. The raw reference SHA-256 is `ea12d290a49eaf61da0234a78fbd37a9ba7455f245c4b038e639bf5818fc3948`.

The deterministic atlas captures emitted positions, logical UVs, geometric light faces, selected sprite names, tint and diffuse flags. The emitter also asserts white vertex color, disabled ambient occlusion and no duplicate side buckets. These are actual Source emitter observations without a rendered window. Source Storage uses matching front/side/top artwork only when inheriting; an explicit face choice uses its ordinary front artwork. Unlike the exact plain Block class, Storage does not join neighboring textures. A missing tile uses the plain material-zero fallback, while an installed default owner uses Cabinet. Native model and rendered acceptance remain separate from this frozen reference.
